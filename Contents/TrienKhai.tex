\subsection{Triển khai Backend}

Phần backend của ứng dụng chatbot tư vấn khách hàng được triển khai theo một chiến lược hiệu quả, tập trung vào việc khai thác hệ sinh thái Platform as a Service của Heroku. Cách tiếp cận này giúp đơn giản hóa đáng kể quy trình triển khai và quản lý hạ tầng, loại bỏ sự phức tạp thường gặp trong việc cấu hình máy chủ thủ công hoặc sử dụng các hệ thống container hóa như Docker. Thay vào đó, Heroku cho phép triển khai trực tiếp mã nguồn thông qua quy trình làm việc tích hợp chặt chẽ với hệ thống quản lý phiên bản Git. Việc lựa chọn Heroku cũng dựa trên trải nghiệm phát triển tốt và khả năng tích hợp dễ dàng với các dịch vụ bổ trợ cần thiết.

\subsubsection*{Kiến trúc hạ tầng và dịch vụ}
Ứng dụng tận dụng hệ thống "dyno" của Heroku để thực thi mã nguồn. Tệp \texttt{Procfile} trong thư mục gốc của dự án định nghĩa các loại tiến trình riêng biệt, cho phép phân bổ tài nguyên và quản lý chúng một cách độc lập:
\begin{itemize}
    \item \textbf{Tiến trình Web (\texttt{web}):} Chạy máy chủ ASGI (Asynchronous Server Gateway Interface) Uvicorn để xử lý các yêu cầu HTTP đến ứng dụng Django, phục vụ các tương tác của người dùng.
    \item \textbf{Tiến trình Worker (\texttt{worker}):} Sử dụng Celery để thực thi các tác vụ nền bất đồng bộ. Các tác vụ này có thể bao gồm việc gửi email thông báo, xử lý các yêu cầu tính toán tốn thời gian, hoặc tương tác với các API bên ngoài mà không làm ảnh hưởng đến thời gian phản hồi của tiến trình web.
    \item \textbf{Lệnh Release (\texttt{release}):} Bao gồm lệnh \texttt{python manage.py migrate}, được Heroku tự động thực thi trong giai đoạn phát hành (release phase) của quá trình triển khai. Điều này đảm bảo rằng mọi thay đổi về lược đồ cơ sở dữ liệu được áp dụng một cách nhất quán trước khi phiên bản mã nguồn mới bắt đầu tiếp nhận lưu lượng truy cập.
\end{itemize}
Kiến trúc đa tiến trình này cho phép ứng dụng xử lý hiệu quả đồng thời các yêu cầu web thời gian thực và các tác vụ nền đòi hỏi tài nguyên tính toán. Hệ thống cũng sử dụng dịch vụ cơ sở dữ liệu được quản lý, ví dụ như Heroku Postgres, để lưu trữ dữ liệu ứng dụng, với lược đồ được quản lý qua cơ chế migration của Django. Các thông tin cấu hình nhạy cảm và biến môi trường được quản lý an toàn thông qua cơ chế Config Vars của Heroku, tách biệt khỏi mã nguồn.

Kiến trúc này cũng tạo điều kiện thuận lợi cho việc mở rộng ứng dụng theo chiều ngang bằng cách điều chỉnh số lượng dyno cho tiến trình \texttt{web} hoặc \texttt{worker} tùy theo nhu cầu tải. Bên cạnh đó, Heroku cung cấp các công cụ tích hợp sẵn để theo dõi hiệu năng ứng dụng và tập trung hóa bản ghi từ tất cả các dyno, hỗ trợ hiệu quả cho việc gỡ lỗi và giám sát hoạt động.

\subsubsection*{Quy trình triển khai}

Quy trình triển khai điển hình trên Heroku được tự động hóa và diễn ra như sau:
\begin{enumerate}
    \item \textbf{Phát triển và commit:} Nhà phát triển thực hiện các thay đổi trên mã nguồn và commit vào Git repository cục bộ.
    \item \textbf{Đẩy lên Heroku:} Sử dụng lệnh \texttt{git push heroku <tên-nhánh>} (ví dụ: \texttt{git push heroku main}) để đẩy các thay đổi mã nguồn lên Git repository từ xa được liên kết với ứng dụng trên Heroku.
    \item \textbf{Kích hoạt quy trình build:} Heroku nhận diện sự kiện push và tự động kích hoạt quy trình xây dựng ứng dụng, bao gồm việc cài đặt các thư viện phụ thuộc và chuẩn bị môi trường thực thi.
    \item \textbf{Giai đoạn release:} Sau khi quá trình xây dựng thành công, Heroku thực thi các lệnh được định nghĩa trong phần \texttt{release} của \texttt{Procfile}.
    \item \textbf{Khởi động lại dyno:} Các dyno đang chạy phiên bản cũ sẽ được dừng và các dyno mới được khởi tạo với mã nguồn và cấu hình đã được xây dựng thành công ở bước trước.
    \item \textbf{Chuyển hướng lưu lượng:} Heroku tự động chuyển hướng lưu lượng truy cập HTTP đến các dyno mới vừa khởi động.
\end{enumerate}
Quy trình tự động hóa này giúp việc triển khai phiên bản mới diễn ra nhanh chóng, đáng tin cậy và giảm thiểu thời gian chết đối với hầu hết các ứng dụng web tiêu chuẩn, nhờ cơ chế chuyển đổi mượt mà của Heroku. Tuy nhiên, cần lưu ý rằng việc sử dụng PaaS như Heroku có thể đi kèm với chi phí vận hành cao hơn ở quy mô lớn và mức độ kiểm soát hạ tầng ít linh hoạt hơn so với giải pháp IaaS.

Dockerfile này được thiết kế để xây dựng một image Docker cho service, sử dụng Ubuntu 22.04 làm base image. 

Chúng tôi bắt đầu bằng việc thiết lập các biến môi trường như múi giờ (TZ=Asia/Ho\_Chi\_Minh) và các cấu hình Python để tối ưu hóa output và quản lý bytecode. Các gói hệ thống cần thiết như python3, pip, và các công cụ biên dịch (build-essential, gcc, g++) được cài đặt qua apt-get để hỗ trợ các dependency phức tạp. UV Package Manager được sử dụng để quản lý và cài đặt dependency từ file pyproject.toml và uv.lock, đảm bảo tính nhất quán. Mã nguồn ứng dụng được sao chép vào thư mục /app. 

Cuối cùng, ứng dụng được chạy bằng Uvicorn trên cổng 8000.

\subsubsection{Triển khai}
Nhóm xây dựng workflow “Build, Push and Deploy AI Service” được cấu hình để tự động hoá quy trình xây dựng ứng dụng. 

Quy trình này bao gồm: đẩy image Docker lên Docker Hub và triển khai lên dịch vụ Render mỗi khi có thay đổi trên nhánh master hoặc khi tạo tag theo định dạng vX.Y.Z. 

Khi có commit hoặc pull request vào master, job build-and-push sẽ checkout mã nguồn, đăng nhập vào Docker Hub, sinh metadata (sha ngắn, semver và tag latest) rồi build và đẩy image. Sau khi build xong, job deploy (chỉ chạy trên nhánh master hoặc trên tag) sẽ xác định tag cần deploy, đợi Docker Hub sẵn sàng rồi gọi API của Render để kích hoạt triển khai mới.

% Trong phần thân tài liệu, chèn YAML:
\begin{lstlisting}[language=yaml]
	name: Build, Push and Deploy AI Service
	
	on:
		push:
			branches: [ master ]
			tags: [ 'v*' ]
	pull_request:
		branches: [ master ]
	
	jobs:
		build-and-push:
		runs-on: ubuntu-latest
		steps:
			- name: Checkout code
				uses: actions/checkout@v3
			
			- name: Docker Hub Login
				uses: docker/login-action@v2
				with:
					username: ${{ secrets.DOCKER_USERNAME }}
					password: ${{ secrets.DOCKER_PASSWORD }}
			
			- name: Generate Docker Metadata
				id: meta
				uses: docker/metadata-action@v4
				with:
				images: davidnguyen7603/coolchatai
				tags: |
					type=sha,format=short
					type=semver,pattern={{version}}
					type=raw,value=latest,enable={{is_default_branch}}
				
			- name: Build and Push Image
				uses: docker/build-push-action@v4
				with:
					context: .
					push: ${{ github.event_name != 'pull_request' }}
					tags: ${{ steps.meta.outputs.tags }}
					labels: ${{ steps.meta.outputs.labels }}
	
		deploy:
			runs-on: ubuntu-latest
			needs: build-and-push
			if: ${{ github.event_name != 'pull_request' && (github.ref == 'refs/heads/master' || startsWith(github.ref, 'refs/tags/')) }}
			steps:
			- name: Checkout code
			uses: actions/checkout@v3
			
			- name: Deploy to Render
			env:
			RENDER_API_KEY: ${{ secrets.RENDER_API_KEY }}
			RENDER_SERVICE_ID: ${{ secrets.RENDER_SERVICE_ID }}
			IMAGE_NAME: davidnguyen7603/coolchatai
			run: |
			# Determine which tag to deploy: semver tag on git-tag, otherwise "latest"
			if [[ "${GITHUB_REF}" =~ ^refs/tags/v([0-9]+\.[0-9]+\.[0-9]+)$ ]]; then
				DEPLOY_TAG="${BASH_REMATCH[1]}"
			elif [[ "${GITHUB_REF}" == "refs/heads/master" ]]; then
				DEPLOY_TAG="latest"
			else
				echo "Unexpected ref ${GITHUB_REF}"
				exit 1
			fi
			
			echo "Deploying image ${IMAGE_NAME}:${DEPLOY_TAG}"
			# Wait until Docker Hub has that tag
			until docker pull "${IMAGE_NAME}:${DEPLOY_TAG}" >/dev/null 2>&1; do
				echo "  ...waiting for ${IMAGE_NAME}:${DEPLOY_TAG} to appear on Docker Hub"
				sleep 5
			done
			
			# Trigger Render deploy
			HTTP_STATUS=$(curl -s -o response.txt -w "%{http_code}" \
				-X POST "https://api.render.com/v1/services/${RENDER_SERVICE_ID}/deploys" \
				-H "Authorization: Bearer ${RENDER_API_KEY}" \
				-H "Content-Type: application/json" \
				-d "{\"imageRef\":\"docker.io/${IMAGE_NAME}:${DEPLOY_TAG}\",\"clearCache\":\"clear\"}")
			if [ "${HTTP_STATUS}" -ne 201 ]; then
				echo "Deploy failed with status ${HTTP_STATUS}"
				echo "--- response body ---"
				cat response.txt
				exit 1
			fi
			
			echo "Deploy triggered for ${IMAGE_NAME}:${DEPLOY_TAG}"
\end{lstlisting}
